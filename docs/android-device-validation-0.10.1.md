# 0.10.1-preview 真机验证

日期：2026-11-13。设备：小米 8 / Android 10 / Adreno 630。
本轮用户重新授权操作手机；只安装引擎 APK、读取现有存档和推进少量测试对白，没有重新导入或修改游戏资源。

## 结论

- 空演示条目导致的启动错误：修复验证通过。UI Preview 原有两个只有零字节 system.arc 的目录不再出现在游戏库，真实导入的 Fureraba 保留并可进入标题。空目录未删除。
- 主应用真实导入的 Fureraba 可进入标题，Kanojo Step 可进入标题并读取快速存档，未遇到用户所述空条目的缺文件错误。进入标题不能代替全流程兼容性验证。
- 立绘对白延迟：没有通过性能验收。选定三句的前后对照未显示实质改善，不把主机像素基准的加速视为手机游玩加速。
- 主应用与 UI Preview 最终均为 0.10.1-preview / versionCode 14，安装包 SHA-256 与交付包完全一致。没有卸载应用。
- 主应用 10 个、UI Preview 1 个 .sud 测试前后 SHA-256 全部一致，没有新增或删除存档。开始测试前已备份存档及每游戏配置。

## 同一场景的点击对照

两次均冷启动主应用，读取同一个 Kanojo Step 快速存档，停在祖母房间、乃绘立绘和「诚如您所言。这批榻榻米是去年才更换的……」这句。
确认画面就绪后注入三次原地 100 ms 触摸，间隔约 2.5 秒；不操作存档按钮。

测量以系统 InputDispatcher 派发抬手为起点，以带毫秒墙钟的系统录屏中下一句文字第一次可见为终点。
atrace 的 realtime_ts 用于对齐系统单调时钟与录屏墙钟。下表为约数，约有一至两帧和系统输入交付误差，录屏也会影响负载。

| 推进内容 | 0.10.0 / code 13 | 0.10.1 / code 14 |
| --- | ---: | ---: |
| 主角回应「哦，刚刚口吻……」 | 86 ms | 103 ms |
| 乃绘立绘变化后「是吗？谢谢您的赞誉……」 | 1113 ms | 1112 ms |
| 主角旁白「从刚才的对话来看……」 | 87 ms | 104 ms |

两个版本在抬手后约 34–42 ms 都已开始清除旧对白，第二句则在下一句出现前有约一秒的立绘演出过程。
这说明该片段的触摸已经及时到达画面，但不能仅凭视频判断这一秒中解码、合成和脚本等待各占多少。
该片段没有复现为“所有有立绘换句都固定延迟 0.3 秒”，因此既不能宣称覆盖了用户的所有场景，也不能宣称原问题已修复。

可复核本地证据（未放入公共源码或发布包）：

- work/runtime/perf-0.10.1/device/timed-baseline-good.mp4、对应 -trace.txt 与 -timing.png。
- work/runtime/perf-0.10.1/device/timed-updated-play.mp4、对应 -trace.txt 与 -timing.png。
- 两个有效 trace 的输入派发记录与时钟同步记录均存在。其他未成功读档或 trace 缺失的试录没有用于此表。

## CPU 采样及后续方向

另用 simpleperf 对两个版本各采样 14 秒，包含立绘对白、图片变化和进入无立绘场景，样本无丢失。
两个采样跨越的对白并不完全相同，因此不用总 CPU 周期或百分比推导升级加速比。
BGI_CbgDecode、Blend32_Plain、Cbg2_Decode 和资源路径查找仍出现在主要开销中；平滑变换不是该次采样的主要热点。

接下来需要把单次推进细分为资源读取/解码、合成、呈现及脚本演出等待，区分性能开销与预定动画时间，再针对主要耗时修复。
另外观察到标题按钮在指针首次移入时可能只改变高亮，需要再次激活；测试读档后均通过截图确认实际场景，后续需单独检查按钮轮询与触摸事件时序。
本轮未据此修改输入语义或缩短游戏脚本等待。
